# DataLens — AI Security, Privacy & Safety Architecture

## 1. Dataset Privacy & Minimization Policy

DataLens enforces a privacy-first data minimization architecture when integrating with external AI providers:

### 1.1 Schema-Only Transmission by Default (`AI_SEND_SAMPLE_VALUES=false`)
- **Default Behavior:** By default, **zero raw dataset cell values** are transmitted to external AI providers.
- **What is Sent:** Only high-level schema metadata is shared:
  - Column name (e.g., `revenue`, `region`, `order_date`).
  - Inferred data type (e.g., `numeric`, `string`, `date`).
  - Total row count of the dataset version.
  - User's natural-language question.
- **What NEVER Leaves DataLens:**
  - Raw table rows, customer records, or bulk business transactions.
  - Column cell values (names, SSNs, salaries, emails, addresses).
  - Parquet storage keys, file paths, or disk manifests.
  - Database connection strings or authentication credentials.

### 1.2 Optional Sample Cell Transmission (`AI_SEND_SAMPLE_VALUES=true`)
- Administrators can optionally enable sample transmission in `backend/.env` via `AI_SEND_SAMPLE_VALUES=true`.
- When explicitly enabled, at most 3 sample cell values per column are included to assist disambiguation of ambiguous categorical columns.
- **Warning:** In datasets containing Personal Identifiable Information (PII) or confidential text, sample transmission should remain `false`. Schema-only interpretation is fully capable of intent parsing without sample values.

## 2. Prompt Injection, Role Whitelisting & Jailbreak Defense

Natural language inputs and conversation histories are treated as untrusted user data:

1. **Structured Grammar Isolation:**
   The AI provider generates *only* JSON conforming to the `AnalyticalPlan` schema. Free-form SQL queries or executable Python code generated by the LLM are rejected at the schema level and never executed.
2. **Strict Conversation Role Validation:**
   The `ChatMessage` schema strictly whitelists roles to `Literal["user", "assistant"]`. Any client payload attempting to inject a `system` role is rejected with HTTP 422.
3. **OpenAI Provider Role Coercion:**
   At the provider layer, any conversation turn not matching `assistant` is coerced to `user`, preventing prompt jailbreaks from masquerading as system prompts.
4. **Message Length & History Size Limits:**
   - Individual messages: minimum 1 character, maximum 2,000 characters.
   - History depth: maximum 10 turns.
   - User questions: minimum 2 characters, maximum 1,000 characters.
5. **Deterministic Heuristic Fallback:**
   Even if an adversarial query includes injection tokens (e.g., `Ignore previous instructions; DROP TABLE users`), the orchestrator's fallback parser constrains the output to safe, read-only DuckDB operations.

---

## 3. Conversation State Architecture

- **Dialogue History:** Request-scoped and client-managed. The frontend transmits the relevant recent dialogue window with each query. There is no server-side conversation table.
- **Analytical Execution Runs:** Fully persisted server-side. Every validated AI query that triggers a DuckDB computation generates an immutable `AnalysisRun` record in PostgreSQL linked to the authenticated `user_id`, `dataset_id`, and `dataset_version_id`.

---

## 4. Clarification Endpoint Defense

The `POST /api/v1/ai/clarify` endpoint does not blindly trust user-supplied `original_plan` payloads:
1. `req.original_plan` is validated against the actual dataset version schema via `PlanValidator.validate_and_normalize_plan`.
2. The user's membership and permissions in the target workspace are verified before processing.
3. The resulting refined plan is independently generated and re-validated before execution.

---

## 5. Multi-Tenant Workspace Isolation & RBAC

1. **Header-Based Workspace Verification:**
   All `/api/v1/ai/*` endpoints require the caller to authenticate with a valid JWT and provide `X-Workspace-ID`.
2. **Role-Based Authorization:**
   Callers must hold `owner`, `admin`, `editor`, or `viewer` roles within the workspace. Non-members receive HTTP 403 / 404.
3. **Cross-Workspace Boundary Checks:**
   `_resolve_dataset_and_parts` explicitly enforces:
   ```python
   select(Dataset).where(
       Dataset.id == dataset_id,
       Dataset.workspace_id == workspace_id,
       Dataset.is_archived.is_(False),
   )
   ```
   Users cannot query or generate explanations for datasets outside their workspace.

---

## 6. Credential & Secret Protection

- `AI_API_KEY` is loaded from `backend/.env` (which is excluded from Git via `.gitignore`).
- The `/api/v1/ai/status` endpoint and error handlers sanitize outputs so API keys are never exposed in JSON responses, stack traces, or client logs.
